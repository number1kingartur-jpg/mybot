## Фича 1 — `/kmstats`: метрики удержания для владельца

**Зачем.** Стратегия «бесплатный инструмент удержания» непроверяема без числа. Сейчас
нигде не считается, сколько людей реально возвращается. Новых сборов данных не нужно —
всё уже пишется в базу с датами.

**Где.** Новый файл `src/metrics.ts`. Никаких новых полей в `DB`, только чтение через
уже существующие `load()`, `getUsers()`, `getWorkoutDates()`, `getMealsForDays()`,
`getWater()`, `getBodyweight()`, `progressSnapshot()` (переиспользовать существующий
подсчёт streak/недели вместо новой реализации).

**Функции в `src/metrics.ts`:**
```ts
export interface RetentionSnapshot {
  usersTotal: number;
  active7d: number;
  active30d: number;
  streakDistribution: { none: number; d1to3: number; d4to6: number; d7plus: number };
  funnelOverlap: { active7dInFunnel: number; active7dTotal: number } | null; // null если файл воронки не найден
}

export function activeUserIds(days: number, todayStr: string): Set<number>;
export function retentionSnapshot(todayStr: string): RetentionSnapshot;
```

- «Активен» = есть запись в `workouts`, `meals`, `water` или `bodyweight` (кроме
  `source==="profile"` — это не действие пользователя, это анкета) с датой в последние N дней.
- `streakDistribution` — по `mealStreak(userId, todayStr).days` для каждого активного за 7д пользователя.
- `funnelOverlap` — читает `BABKI\bot\data\users.json` (путь: подняться от `mybot` на уровень
  BABKI, `../bot/data/users.json`; обернуть в try/catch, файла может не быть — тогда `null`,
  не падать). Формат файла — объект/массив с `telegram_id`; сверить с активными за 7 дней
  KINGMODE по числовому Telegram ID (это общий ключ между двумя ботами). Если формат на деле
  отличается от ожидаемого — прочитать реальный файл `BABKI\bot\data\users.json` перед тем как
  писать парсинг, не гадать по памяти.

**Бот-команда** в `src/index.ts`, рядом с другими owner-командами (см. `isOwner(ctx.from!.id)`,
например у `/stats`, если такая уже есть — если есть, расширить её, не плодить дубль команд;
если нет — добавить `/kmstats`). Формат ответа — обычный HTML-текст Telegram (как остальные
ответы бота), без тире, без Ё, числа с пояснением, не только цифры:

```
Удержание KINGMODE
Всего пользователей: N
Активны за 7 дней: N (из них с серией 7+ дней: N)
Активны за 30 дней: N
Из активных за 7 дней уже клиенты воронки: N из N
```

**Проверка.** Новый `scripts/check-metrics.mjs` по образцу `scripts/check-guard.mjs`
(импорт `dist/metrics.js`, синтетическая DB через временный `DATA_PATH`, набор
`check(name, ok, detail)`). Добавить в цепочку `build` в `package.json` после
`check-db.mjs`.

## Фича 2 — фотопротокол прогресса тела

**Зачем.** Единственный крупный разрыв против конкурентов (Прайм-тело, Cal AI и др.),
явно зафиксированный в `ORDERS/KINGMODE.md` («Задача №4», не начата). Сильнейший крючок
удержания в этой категории — визуальное сравнение «было/стало».

**Хранение.** Файлы на том же Volume, что и база (`/data`, локально — рядом с `data.json`):
`<DATA_DIR>/photos/<userId>/<id>.jpg`, где `DATA_DIR = path.dirname(DB_PATH)`. Не плодить
новую переменную окружения — выводить из уже существующего `DATA_PATH`.

**Данные** — новое опциональное поле в `DB` (`src/db.ts`), по тому же паттерну, что
`water?: WaterEntry[]`:
```ts
export interface ProgressPhotoEntry {
  id: string;
  userId: number;
  date: string;       // YYYY-MM-DD, дата съёмки (не загрузки)
  angle: "front" | "side" | "back";
  path: string;        // абсолютный путь на диске
  sizeBytes: number;
  createdAt: string;   // ISO, момент загрузки
}
```
Добавить `progressPhotos?: ProgressPhotoEntry[]` в `interface DB`, `emptyDb()`, `readAt()` —
строго по образцу того, как уже добавлено поле `water` (см. миграцию `parsed.water ?? []`).

Функции в `db.ts`, использующие существующий `save()` (атомарная запись — не писать файл
изображения и не обновлять DB одновременно без разбора: **сначала** записать файл на диск,
**потом** зафиксировать запись в базе атомарным `save()`; при ошибке записи файла — не
трогать базу вообще, вернуть ошибку вызывающему):
```ts
export function addProgressPhoto(entry: Omit<ProgressPhotoEntry, "id" | "createdAt">): ProgressPhotoEntry;
export function listProgressPhotos(userId: number): ProgressPhotoEntry[];
export function getProgressPhoto(userId: number, id: string): ProgressPhotoEntry | undefined; // только своя запись
export function deleteProgressPhoto(userId: number, id: string): boolean; // удаляет файл с диска И запись из базы; если файл уже отсутствует — не падать, всё равно убрать запись
export function progressPhotoUsage(userId: number): { count: number; bytes: number };
```

**Лимиты** (`src/guard.ts`, рядом с `PHOTO_GLOBAL_MAX` — тот же файл и стиль):
```ts
export const PROGRESS_PHOTO_MAX_COUNT = 60;         // на пользователя
export const PROGRESS_PHOTO_MAX_BYTES = 150 * 1024 * 1024; // на пользователя
```
При превышении — сервер отвечает понятной ошибкой с текущим количеством/объёмом и
предложением удалить старые. **Не удалять чужие фото автоматически** — это фотографии
тела, тихое удаление без действия пользователя недопустимо.

**API** в `src/server.ts`, тем же способом авторизации, что остальные эндпоинты
(`auth(req, botToken)` → `WebAppUser`, отказ = `401`, лог без самой подписи — см. текущую
функцию `auth()` как образец):

- `POST /api/progress/photo` — `multipart` или base64 JSON (посмотреть, как уже принимается
  фото еды в существующем эндпоинте распознавания, и повторить тот же способ приёма файла —
  не изобретать новый формат приёма для одного эндпоинта). Поля: `angle`, `date`, файл.
  Проверить лимиты (`progressPhotoUsage`) до записи на диск. Путь на диске строится
  **только** сервером из `userId + crypto.randomUUID() + ".jpg"` — из клиентских данных в
  путь не подставляется ничего.
- `GET /api/progress/photos` — список записей текущего пользователя (из `initData`, не из
  параметра запроса) с полем `url` — **не прямая ссылка на файл**, а
  `/api/progress/photo/<id>?token=<подписанный>`.
- `GET /api/progress/photo/:id` — отдаёт байты изображения. Подпись токена: тот же секрет,
  что `verifyInitData` уже использует для HMAC (переиспользовать, не заводить новый секрет),
  HMAC от `id + userId + expiry`, срок жизни 15 минут, при протухшем/неверном токене — 403,
  не редирект и не молчаливая заглушка.
- `DELETE /api/progress/photo/:id` — тот же `auth()`, удаляет только если `userId` записи
  совпадает с `initData.user.id`.

**Веб-интерфейс** (`webapp/js/`, `webapp/css/app.css`) — по существующей структуре разделов
(«Профиль» уже содержит дневник веса — см. `docs`/`webapp` за примером, как там устроена
вкладка, и повторить тот же приём для фотопротокола, не изобретать новый паттерн навигации):
раздел внутри «Профиль», сетка миниатюр по датам с фильтром по ракурсу (спереди/сбоку/сзади),
режим сравнения — выбрать две карточки, показать рядом, кнопка загрузки под каждый ракурс,
кнопка удаления на карточке с подтверждением (не удалять по одному тапу без подтверждения —
это необратимо и это фото тела). Текст интерфейса — без тире и Ё, как во всём остальном
приложении.

**Проверка.** `scripts/check-progress-photos.mjs` по образцу `check-guard.mjs`/`check-db.mjs`:
лимит по количеству, лимит по объёму, отказ доступа к чужой записи (другой `userId`),
просроченный/неверный токен, физическое удаление файла при `deleteProgressPhoto`. Добавить
в `build`-цепочку.
